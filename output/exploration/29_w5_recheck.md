## 2. 数据流 / 判据"量的是什么"

| 判据 | 量的东西 | 为什么与时间无关 |
|---|---|---|
| W5-② 名文本缓存 | `SurfaceCache("name_text", 32 MiB, 1024)` 的 `hits/misses/evictions/items/bytes` | 缓存自带计数器（`app/cache_store.py:37-39,106-118`） |
| 强压场景 | 207 台风**逐个**调 `sim.draw_typhoon_name(surf, ty, x, y)`，x/y 按 20 列循环 | 调用次数与键集**只由台风数决定** |
| 像素等价（地图/陆地） | 512×288 重采样指纹 + 逐像素差 | 确定性渲染 |
| 像素等价（名字） | 同一批台风、同一位置、画到同尺寸空白面；比 ① 不透明底合成后的 RGB sha ② 仅 `alpha>0` 处 RGB sha ③ ink 包围盒 | 纯确定性绘制 |
| 物理门 | ufunc 调用/全网格/元素数 + `setprofile` C 调用 + 状态指纹 | 上一轮已证跨核逐位可复现 |

> **为什么名字这一项要算三个 sha**：紧裁（轮七）会让**透明区里残留的 RGB** 变化，
> 那种差异**不可见**。所以必须用"合成到不透明底"或"只看 alpha>0"来判可见等价 ——
> 这也是 sim-core 说的"不透明画布 sha256 逐字节相同"的口径（我独立复算了）。

## 3. 核心结果

### 3.1 【实测】W5-② 强压场景：`evictions = 0` ⇒ **PASS**

`name_after_all_tys`（原始 JSON 字段，未加工）：

```
BEFORE : {"items":256,"bytes":16015496,"max_bytes":33554432,"hits":771,"misses":801,"evictions":548}
AFTER  : {"items":528,"bytes":33513616,"max_bytes":33554432,"hits":843,"misses":729,"evictions":204}
AFTER3 : {"items":709,"bytes":22909012,"max_bytes":33554432,"hits":866,"misses":706,"evictions":0}
```

**判读**：
- **`evictions: 548 → 204 → 0`**。判据 `== 0` ⇒ **PASS**。
- **`items = 709 = misses(706) + 3`** ⇒ **工作集被完整保留**（0 驱逐的直接含义）：
  706 次 miss 全部是"首次装入"，之后再没有被迫腾位。
- **字节 22,909,012 / 33,554,432 = 68.3%**，余量 **10.15 MiB**（不是"刚好塞下"）。
- 每键平均 **32.3 KB**（BEFORE 62.6 KB / 上一版 63.5 KB）⇒ 轮六缩小辉光边距、
  轮七裁到 `alpha>0` 包围盒，两次都在缩**表面尺寸**（这正是"改键/改表面"而不是"加大上限"）。
- 另一处旁证：`name_cache_before` 的 bytes 从 **179,996 → 88,140**（−51%），
  说明**每个名字表面本身**确实小了一半。

**【实测】与 sim-core 推算的对账**：

| | sim-core 推算 | 我的实测 |
|---|---|---|
| 工作集字节 | ≈22.4 MB | **22.91 MB**（22,909,012 B） |
| 相对误差 | — | **+2.3%** |
| 是否 0 驱逐 | 预期 0 | **实测 0** |

⇒ 推算与实测一致，**这条 unresolved 可以关掉**。

## 5. 我用了什么测法 / 允许的结论强度

- **允许**：缓存计数（hits/misses/evictions/items/bytes）、模块在不在 `sys.modules`、
  状态指纹、像素 sha —— 这些都是**确定性量**，本报告的全部判定都基于它们。

  同一 x/y 循环**；连"台风顺序"都一样（8 例抽样名单逐个相同）。

## 6. 观察到的问题 / 风险 / 不一致

### 6.1 【实测】上一版为什么是 204 而不是 0 —— 不是判据不同，是**两次改动到位与否**

- 上一版（轮 1-5 之后）字节 **33,513,616 / 33,554,432 = 99.88%**，**预算已被顶满** ⇒ 必然有驱逐。
- 轮六（`GLOW_PAD_TIGHT`）+ 轮七（`SURF_TIGHT_CROP`）把每键从 63.5 KB 压到 32.3 KB
  ⇒ 同一 709 个键只需 22.9 MB ⇒ 0 驱逐。
- ⇒ **这不是"我的判据变松了"**：判据始终是 `evictions == 0`；变的是**被测量本身**。
  我把两次数字都留在 §3.1，便于审计。

### 6.2 【实测】"加上限"与"减尺寸"的对比（给下一轮的结论）

| 做法 | items 上限 | 每键字节 | 结果 |
|---|---|---|---|
| 轮 1-5：只把条目上限 256 → 1024 | 1024 | 63.5 KB | 驱逐 548 → 204（**预算顶满，未达标**） |
| 轮 6+7：缩表面（辉光边距 + 紧裁） | 1024 | **32.3 KB** | 驱逐 **0**，余量 10.15 MiB |

⇒ **"改表面尺寸/键"才解决根因；"加上限"只是换了个瓶颈**（这条与我上一轮 §6.1 的保留意见一致，
现在有了实测对照）。

### 6.3 【未能验证】预览框定位 6/6 —— 我没能独立复算那份清单

- **我没做什么**：没有重建 sim-core 的"6 个消费点逐个比矩形"的探针（那需要复刻他们的场景与对照数据）。
- **我做了什么（替代性但更强的一侧）**：
  1. 读了消费链：`app/name_pos_dialog.py:327-332` 用 `s._name_surf_off(nm, col, nf)` 的
     **`(nsurf, noffx, noffy)`** 建 `name_rect = Rect(ox-noffx, oy-noffy, *nsurf.get_size())`；
     预览**真正落笔**走 `sim.draw_typhoon_name(...)`（`_draw_preview`，`name_pos_dialog.py:585`）
     ⇒ **预览与地图绘制共用同一个偏移来源**，不存在"两套口径"。
  2. **端到端可见像素检查**（§3.2）：8 例名字在**两棵树**上画到同一位置，
     不透明合成与 ink-only 两种 sha **逐字节相同** ⇒ 名字落屏位置与像素**零变化**。
- **结论**：**未独立复算 6/6 清单本身**；但**独立验证了它成立的前提**
  （绘制可见像素零变化 + 预览/绘制同源偏移）。**建议**：若要把这条也钉死，
  把"逐个消费点比矩形"做成脚本（6 个断言），我可以在下一轮复用。

### 6.4 一条值得写下的方法论

轮七把**表面裁小**会让"整张 RGBA 的 sha"变化，但**可见像素不变**。
本轮因为同时算 `sha_opaque` / `sha_ink` / `all_sha` 三个量才没被误导 ——
**任何"像素等价"判据必须明确是"可见量"还是"含透明区的原始量"**。

### ✅ 值得保留的现状
- `SurfaceCache` 自带 `hits/misses/evictions/bytes` ⇒ 本轮**零插桩**拿到全部判据。
- `GLOW_PAD_TIGHT` / `SURF_TIGHT_CROP` 两个开关**都保留了 False 回退**（`_draw_icon_mixin.py:155,201`）
  ⇒ 若画质有问题可一键回退，这是正确的做法。
- 物理门（`w5_det`）在**三轮改动之后仍是 `310d4efe…` 逐位相同** ⇒ 这批改动确实没碰内核。
