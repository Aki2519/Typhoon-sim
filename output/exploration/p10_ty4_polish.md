## 2. ① 图例按 §5 缩放（B12）

```
row = 27 × H/1080 ;  dot = 11 × H/1080 ;  pad ≈ dot/2
x_dot(左缘) = W − pad − dot ;  y0 = H − row×n − pad ;  行中心 y = y0 + i×row + row/2
```

## 3. ② 绘画顺序：`points_top` 就是 `Priority=2`（**保留默认**）

**§6 的 `Priority=2`** = "所有轨道的线画完后, 再统一补画所有轨道的定点（定点置顶）"；`Settings.ini` 现为 `2` ⇒ 参考图里点在线之上。
**我们的 `_draw_tracks`**（`paint_render.py:532-560`）：`points_top=True` 时**先跑一遍画所有线、再跑一遍画所有点** ⇒ **与 Ty4 语义逐字一致** ✅

**为什么把默认留在 `simult`**（三条依据，全部实测）：
1. **Ty4 的用法是"一次一个文件"** ⇒ 单台风下 `simult` 与 `points_top` **像素完全相同**（实测：单台风两次 sha 都是 `6de8c11c…`）⇒ **默认已经给出 Priority=2 的视觉结果**。
2. 5 个基准台风本来就是**单台风渲染**，`simult` 与 `points_top` 在它们上面**也没有差别**（4 台风实测同 sha `4f8c9a53…`，因为 ink 不重叠）。
3. 差异**只在"不同台风的线与点相互覆盖"时才出现**：构造两条交叉轨迹、并在交叉点放一个定位点后，两者 sha 不同、**差异 43 px**（正是被另一条线盖住的那个点）。此时 `points_top` 才是 Ty4 的样子。
⇒ 结论：**默认改动只会影响"多台风同图且 ink 重叠"这一小类**，却会改变既有导出；`points_top` 已作为选项存在（P5 有暴露）。**保留默认 + 在 UI 里可选** 是更稳的取舍。

## 4. ③ `all_points=False`：Ty4 语义是"只画线不画点"

**查清结果**（§11.2）：`AllPoints` = 是否画每个定位点；`t4_render.py:365`: **`0 ⇒ 只画线不画点`**。
**我们原来的实现**：`pool = pts[-1:]` = **只画最后一个定位点** —— 与 Ty4 不同，且与 UI 上"显示所有定位点"的开关含义也不吻合。
**已改**：`pool = pts if self.all_points else []`（空池 ⇒ 一个点都不画）。
**实测**：同一台风 `all_points=True` 非底色像素 **11321**（线+点）→ `False` **4524**（只剩白线）。
**默认 `all_points=True` ⇒ 默认输出不变**；⚠ **P5 请把 UI 文案从"仅最后定位"改成"不画定位点"**（若原来是那样标的）。

```python

```
**实测**：`draw_rad="last"` 现在与 `draw_rad="none"` **像素完全相同**（11321 = 11321）并打出一次告警；改前（state_v8）同一用例是 **11394** px ⇒ 多出来的 **73 px 就是那圈编造的半径**。
**没有**去实现 §8 的三档灰扇形去喂假半径 —— 那等于"用保真的外衣掩盖数据造假"。
**出路（写给下一步）**：真实 `RAD/BP/TK` 数据到位后按 §8 实现（r34/r50/r64、单位海里 `/60` 转度、`dlon=rad·sinθ/max(0.2,cos lat)`、45° 扇形、灰 `(232,232,232)` alpha 90/60/40、画在线之前）。**默认 `draw_rad="none"` ⇒ 默认输出不变。**

### 5.1 ⚠ 用户可见后果（Lead 指定必须写清）

**现状：`draw_rad` 是一个"看起来有、实际没有效果"的开关。**

| 用户操作 | 实际效果 |
|---|---|
| `draw_rad = "none"`（默认） | 不画风圈 —— 与改前一致 |
| `draw_rad = "all" / "last" / "tropical"` | **什么都不画** —— 与 `"none"` **输出逐像素完全相同**（实测同 sha、同为 11321 px） |

⇒ **用户会以为开关坏了**（其实不是：是**没有数据可画**）。这一点必须在 UI 上说清，否则我们只是把"画假圈"换成了"更诚实的静默"。

**为什么现在是空操作**：Ty4 的风圈半径只来自 ATCF bdeck 的 **`RAD/BP/TK` 行**（象限风速半径）；
本机全库 grep **没有这些行**（TY4_SPEC §8 也因此**没能用真实数据验证风圈**，只有合成样本 `_selftest\rad_sample.txt`）。
原来那句 `rad34 = p.get('r34', 0) or max(0, int(wind * 0.5))` 在无数据时**用风速编了一个半径** ——
那个圈看起来像 Ty4，但代表的是一个**不存在的气旋尺度**，比"不画"更危险（会被当成真实尺度读图）。
**所以本轮改成不画，而不是改得像。**

**什么条件下会真正生效（三段式）**：
1. **数据**：拿到含 `RAD` 行的 bdeck（或 ATCF `BP/TK`），解析进 `Fix.radii`（NE/SE/SW/NW × 34/50/64 kt 共 12 个数）；
2. **几何**：半径从**海里**换算（`/60.0`），并做 `dlon = rad·sinθ / max(0.2, cos(lat))` 的经向修正（高纬不再放大）；
3. **样式**：§8 是 **3 档 45° 灰色扇形**（`(232,232,232)`、alpha 90/60/40、r34 先画 r64 后画 ⇒ 小半径压大半径上，且**画在线之前**）。
   ⚠ **我们现在画的仍是"单档黑色 `(0,0,0,120)` 圆环"** —— 即便将来接上真实数据，**样式也仍需一并改成 §8 的扇形**，否则会变成"有数据但仍然不像 Ty4"。
   本轮**没有**先做扇形：无数据可验证 ⇒ 会写出一段"没人能判断对不对"的代码。

**给 P5 的建议文案**：把该下拉标注为「风圈（当前数据无 RAD 风圈数据，暂不生效）」，或在无 `r34` 时置灰 —— **关键是别让用户以为它生效了**。
