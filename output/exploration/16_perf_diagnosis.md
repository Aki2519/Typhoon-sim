> 生成：2026-10-02 · 对象：**整个工作区程序**（`main.py` 那个 pygame 应用），不只是模拟模式
> 方法：`perf-optimize` 技能的 **E. 只诊断不改** —— 本文件**不含任何代码改动**，只给问题清单、优先级、预期收益/成本

## 摘要

**结论一句话：模拟器的性能问题不是"整体慢"，而是三个互不相同的靶子，而且必须先修测法——否则改了什么都不知道。**

| 靶子 | 现状 | 性质 |
|---|---|---|
| **① 启动** | `TySim()` 构造 **5218 ms = 全启动 88.3%** | 单线程 CPU 密集 + 646 MiB，**有真问题** |
| **② 内存** | 单实例 RSS **646 MiB**，而本机**可用仅 1.6 GiB**；多条缓存的最坏上界合计 **1.9–2.6 GB** | **结构性 OOM 风险**，最该先动 |
| **③ 日常渲染** | MODE_NORMAL 稳态 **p50 11.5 ms**、季节峰值（12 个台风同时存活）**p50 30.3 ms** | **不用救**，已经健康 |

另有一个**尚未触发但一旦触发极惨**的缩放悬崖：图标名文本缓存条目上限 256，而 207 个台风全激活时帧内工作集是 **708** ⇒ 每帧 768 次驱逐 + **54,384 blit（占全部 blit 99.2%）**。当前数据最多 12 个同时存活，够不到；但它是"改一个数字"就能拆掉的定时炸弹。

**并且，这个项目对自己性能的现有认知是错的。** 详见 §1——那条被引用了很多次的 **1690.7 ms/步基线，其实是"集合步 + 非集合步"的混合均值**，而文档里"forecast 默认关"的说法与它自己的 cProfile 互相矛盾。

## 1. 第一优先级：修测法（不做这个，后面全是猜）

### 1.1 项目已经踩过这个坑，并撤回过自己的结论

`output/sim/_reference/PERF_BASELINE_R158.md:155-295` 白纸黑字：

- 同一份代码连测三次：**1008 / 1114 / 1409 ms/步**（漂移 40%）
- 同进程交错 A/B：974 / 1489 / 1498 / 971 / 1211 / 1026 ms（波动 53%）
- ⇒ **「#1 的 1.48x 与 #2 的 1.13x 取消」**
- A/A 自检极差 **75.6% / 72.6%**（判据 15%，超标 5 倍）
- 结论句：「**本机当前处于重载争用状态……任何在此状态下得到的加速比只能记为「无法从噪声中分离」**」

他们把它归因于"重载争用"。**这个归因不完全对。**

### 1.2 Lead 的三个实验：两个假设被证伪

| 假设 | 做法 | 结果 |
|---|---|---|
| ①「墙钟受调度延迟污染，用 CPU 时间就稳了」 | 同轮报 `perf_counter` 与 `process_time` | ❌ **证伪**：极差 324.9% vs 324.3%，两者逐轮比 ≈**1.00** ⇒ 进程纯 CPU 密集、没在等 IO |
| ②「算力缩放可以用参考负载约掉」 | 测前跑定长纯 CPU 校准负载，取比值 | ❌ **证伪**：归一化后 756% vs 原始 780%，压低 **1.0 倍** |
| ③「线程在 P 核 / E 核之间迁移」 | `SetProcessAffinityMask` 绑核对比 | ✅ **成立**（见下） |

实验 ① 之所以失败，恰好由 ③ 解释：**E 核完成同样指令要花更多 CPU 秒**，所以 CPU 时间跟着墙钟一起涨。

### 1.3 根因：混合架构 CPU + 调度器迁移

硬件是 **13th Gen Intel i7-13700HX = 8 P 核 + 8 E 核**（24 逻辑处理器）。

sim-run 的核扫描给出了**零重叠**的两档（确定性事实）：

| 核组 | ms/步 |
|---|---|
| **逻辑 0–15（P 核）** | **120–145** |
| **逻辑 16–23（E 核）** | **217–234** |
| 比值 | **1.90×** |

⇒ Windows 把单线程在两类核之间迁移，就是那"8 倍跳变"与"889% 极差"的来源。

### 1.4 但"绑核"不是无脑正确 —— 四个人的结论曾经互相矛盾，现在有答案了

| 谁 | 被测负载 | 结论 |
|---|---|---|
| Lead | `V.sim_step`（单线程 CPU 密集） | 绑单核 8 → 极差 **4.6%** ✅ |
| app-sim | `TySim()` 构造 | 绑单核 8 → **慢 2 倍**、极差 11.1% ❌；绑 **0–7** → 极差 **1.7%** ✅ |
| app-feat | `TySim()` 构造 | 绑核 vs 不绑：5.00 s vs 7.30 s（**+46%**）❌ |
| sim-run | 合成 6 线程负载 | 绑单核 → **53.4 → 131.6 ms（2.5× 慢）**，`wall/cpu` 0.23→1.05 ❌ |

**裁决（sim-run 给出，四条规则）：**

1. **多线程负载绝对不能绑单核** —— 会被串行化（实测 2.5× 慢）。
2. **单线程负载绑"P 核组"（0–15 或 0–7）**，不要绑单核 —— 绑核**不排他**，单个核随时可能被系统线程偷走（实测 c8 上 `wall/cpu` 到过 **1.93**，即核被偷一半）。绑核组的意义是"不被某一个繁忙核拖死"。
3. **"哪个核最快"本身不可复现**：同脚本同参数两次运行，mask 0–15 的 min 从 **201.7 → 428.9**（2.13×），最优核组从 0–15 换成 c8。⇒ **这就是四个人结论互相矛盾的原因——谁都没测错，是机器的"最优"在变。**
4. **任何 A/B 必须交错**：app-sim 顺序跑两臂得 16% / 46%，改交错后降到 3.9% / 11.1% ⇒ **臂顺序漂移是离散度主因**。

### 1.5 修正后的对项目认知：那条 1690.7 ms/步的基线是错的

**Lead 与 sim-run 联合更正的三个层次：**

**① 我（Lead）先误判了一次。** 我看到"8 轮单调下行 8 倍"，判成 warm-up 爬坡。sim-run 改成**逐 10 步**采样后证伪：

- **第 1–10 块就是整个 run 最快的块**（未绑核 163.5 ms/步）⇒ **根本没有冷态→稳态爬坡**
- 8 倍跨度**精确对齐 `n_alive 0→1`**（步 11–20 = 3128 ms；步 121–140 = 3275 ms）
- 我那个"8 轮 × 15 步 = 120 步"的采样窗口**恰好套在一个台风生命周期上，产生了混叠**

**② 真因是集合预报随台风生死开/关。**

| | 集合步（有台风存活） | 非集合步 |
|---|---|---|
| 每 6h 物理步 | **4.4–8.2 s** | **0.4–0.6 s** |

**③ ⇒ `PERF_BASELINE_R158.md` 的 1690.7 ms/步是这两者的混合均值**，比例由 RNG 的台风生死决定。任何改动只要动了生成/消亡时刻就会改这个数，**与快慢无关**。

**独立佐证（cProfile 调用次数，确定性）**：`_env_update_impl` ncalls **24（forecast 开）vs 12（关）**；`forecast_env_series` cumtime 占 **44.3%**。

**而且同一份文档 8 行之内自相矛盾**（Lead 已核实）：

| 位置 | 内容 |
|---|---|
| `PERF_BASELINE_R158.md:73` | 「它由 `params['forecast']` 控制(**默认关**)」 |
| `PERF_BASELINE_R158.md:72` | 自己的 cProfile：「`forecast_env_series` 单次调用 4.94 s(占 41%)」 |
| `core.py:5101` | 实际是 `.get('forecast', True)` ⇒ **默认开** |
| `tools/perf_baseline_r158.py:31` | 只传 `{'seed': ...}`，**不传 forecast** ⇒ 吃默认 True |

### 1.6 ⇒ 结论：主指标必须是**与时间无关的确定性量**

sim-run 已交付并**验证逐位可复现**（P 核 c8 与 E 核 c16 两遍完全相同）：

| 指标 | 值 |
|---|---|
| ufunc 调用次数 | **3,162** |
| 全网格操作数 | **3,026** |
| 元素数 | **1,022,286,160** |
| `setprofile` C 调用 | **1,683** |
| cProfile top15 | 逐行相同 |
| 状态指纹 | `dce6fd26…` |

（只有 `tracemalloc` 有 ±0.7 KB 抖动 ⇒ 不作硬门。）

**并已在 3 步与 35 步两个尺度上验证"每步速率"完全相同** ⇒ 指标可跨尺度外推。

### 1.7 验收协议（以后任何优化照这个走）

1. 量 `wall/cpu` 判并行度 —— **`wall/cpu > 1.15` 时该段测量作废**（核被偷）。
2. 单线程负载 → 绑 P 核组；多线程负载 → **必须**绑核组（绝不绑单核）。
3. 跑 A/A 自检：极差 ≥15% 时**不许报计时**。
4. **主判据用确定性指标**（调用次数 / 缓存 hits-misses-evictions / 元素数 / 指纹），计时只作区间。
5. 必须留**回退路径**（配置开关或保留旧实现可切换）。
6. 一次只改一个变量。

### 明确的"白做工"（不构成风险，但可省）

- `should_draw_typhoon` 在正常模式对**全表 207 个**逐个判定，只有 1 个能过。
- 正常模式稳态每帧仍解码 **3.5 次 video** + 2.8 次 grab，而屏幕上只有 1 个图标（`:456`、`:840 budget=3` 预载）。
- 绘画一次全局图的确定性工作量 = **15,933 图元 / 2 Surface(4.1 MiB) / PNG 81.1 KiB** —— **算法侧健康**。

## 4. 优化路线图（建议顺序）

**先修测法与内存，因为它们一个是前提、一个是硬约束。**

| 阶段 | 做什么 | 为什么这个顺序 |
|---|---|---|

| **3** | 第 2 层缓存/懒加载（#8、#9、#10） | 需要改调用点，回归面比第 1 层大 |
| **4** | 模拟模式图层（第一轮数据：整层 240 ms / `sst` 冷 2589 ms / `ridge` 热无缓存） | 只影响模拟模式用户；且第一轮的 `PERF_MEMO_PLAN.md` 已列好候选与"不适合缓存的块" |
| **5** | 第 3 层 #13 预热粒度 | 体验问题，非阻塞 |

**每个阶段结束后**：跑确定性指标对比 + A/A 自检；功能回归用 `pytest`（注意：`tests/` 被 `.gitignore` 忽略但磁盘上在，且 `test_sim_mode.py` 上游一次没跑完）。
